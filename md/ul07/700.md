# <img src="../../img/laravel_azul.svg" width="40"> 11.0. Introducción

En la unidad 10 construimos una API REST de notas. En esta unidad la consumiremos desde un **frontend en Vue**: una aplicación de una sola página (**SPA**) que se ejecuta en el navegador, pide los datos a la API y pinta la interfaz. El resultado es una **aplicación web híbrida**: Laravel en el servidor y Vue en el cliente.

## 1. Arquitectura

```text
[ Navegador: SPA en Vue ]  ── HTTP (axios) ──>  [ API Laravel ]  ──>  [ Base de datos ]
   pinta pantallas,                               valida, aplica reglas
   formularios, botones                           y permisos, consulta la BD
                          <──── JSON ────────
```

> **Idea clave**: Vue no habla con la base de datos. Vue habla con la API, y la API habla con la base de datos.

| Parte | Responsabilidad | Tecnología |
| --- | --- | --- |
| **Backend** (DWES) | Datos, validación, autenticación, permisos | Laravel + Sanctum |
| **Frontend** (DWEC) | Interfaz, navegación, experiencia de usuario | Vue + Vite + axios |
| **Contrato** | Rutas, formato JSON y códigos de error | Documentación de la API (apartado 10.3) |

Si el contrato no cambia, cada parte puede evolucionar sin romper la otra. Es la base de un **proyecto intermodular**: en DWES se desarrolla la API y en DWEC se consume.

## 2. Un ejemplo mínimo

**Backend**: la ruta `GET /api/notes` de la unidad 10 (sin autenticación, como al final del apartado 10.2) devuelve:

```json
{
    "data": [
        { "id": 1, "titulo": "Comprar pan", "estado": "Pendiente" },
        { "id": 2, "titulo": "Estudiar Vue", "estado": "Completada" }
    ]
}
```

**Frontend**: un componente Vue la consume y pinta la lista.

```vue
<script setup>
import { ref, onMounted } from "vue";
import axios from "axios";

const notes = ref([]);
const loading = ref(true);
const error = ref("");

onMounted(async () => {
    try {
        const res = await axios.get("/api/notes", { headers: { Accept: "application/json" } });
        notes.value = res.data.data;
    } catch (e) {
        error.value = "No se han podido cargar las notas.";
    } finally {
        loading.value = false;
    }
});
</script>

<template>
    <p v-if="loading">Cargando…</p>
    <p v-else-if="error">{{ error }}</p>
    <ul v-else>
        <li v-for="note in notes" :key="note.id">{{ note.titulo }} ({{ note.estado }})</li>
    </ul>
</template>
```

Si la base de datos cambia, si se añaden reglas o permisos, Vue no se entera mientras el JSON siga siendo el mismo. Y una app móvil podría usar exactamente la misma API.

## 3. ¿Cómo se autentica una SPA?

En el apartado 10.4 usamos **tokens Bearer**. Funcionan desde una SPA, pero obligan a guardar el token en JavaScript (`localStorage` o memoria):

| | Token Bearer | Cookie de sesión (Sanctum SPA) |
| --- | --- | --- |
| Dónde se guarda | En JavaScript (`localStorage`, memoria) | En una cookie **HttpOnly** que JavaScript no puede leer |
| Riesgo si hay XSS | Un script malicioso puede robar el token | El script no puede leer la cookie |
| Envío en cada petición | Hay que añadir la cabecera `Authorization` | El navegador envía la cookie automáticamente |
| Protección CSRF | No hace falta | Sí: cookie `XSRF-TOKEN` + cabecera `X-XSRF-TOKEN` |
| Ideal para | Postman, apps móviles, servidores | SPA en el navegador **en el mismo dominio** que la API |

Para una SPA en el navegador, Sanctum recomienda su **modo SPA**: autenticación con la **sesión de Laravel** a través de cookies.
