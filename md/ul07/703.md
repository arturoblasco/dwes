# <img src="../../img/laravel_azul.svg" width="40"> 11.3. Autorización

Ya sabemos **quién** es el usuario (autenticación). Ahora decidimos **qué puede hacer** (autorización): cada usuario solo ve y modifica sus notas, y un administrador puede con todas.

| | Pregunta | Si falla |
| --- | --- | --- |
| **Autenticación** | ¿Quién eres? | `401 Unauthorized` |
| **Autorización** | ¿Puedes hacer esto con este recurso? | `403 Forbidden` |

> La seguridad real está siempre en el **backend**. Vue solo adapta la interfaz para que el usuario no vea botones que no puede usar.

## 1. Propietario de cada nota

Cada nota pertenece a un usuario. Añadimos la clave foránea:

```bash
php artisan make:migration add_user_id_to_notes_table
```

```php
public function up(): void
{
    Schema::table('notes', function (Blueprint $table) {
        $table->foreignId('user_id')->nullable()->after('id')
              ->constrained()->cascadeOnDelete();
    });
}

public function down(): void
{
    Schema::table('notes', function (Blueprint $table) {
        $table->dropConstrainedForeignId('user_id');
    });
}
```

Es `nullable` para no romper las notas que ya existen. Puedes asignarles un propietario con Tinker: `App\Models\Note::whereNull('user_id')->update(['user_id' => 1])`.

Relaciones en los modelos (unidad 8):

```php
// app/Models/User.php
public function notes(): HasMany
{
    return $this->hasMany(Note::class);
}

// app/Models/Note.php
public function user(): BelongsTo
{
    return $this->belongsTo(User::class);
}
```

## 2. Roles

Para distinguir administradores, añadimos un campo `role` a `users`:

```bash
php artisan make:migration add_role_to_users_table
```

```php
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->string('role')->default('user')->after('email');
    });
}

public function down(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->dropColumn('role');
    });
}
```

```bash
php artisan migrate
```

En el modelo `User`, un método que hace el código más legible:

```php
public function isAdmin(): bool
{
    return $this->role === 'admin';
}
```

!!!tenencuenta "No añadas `role` a `$fillable`"
    Si `role` estuviera en `$fillable`, alguien podría registrarse enviando `"role": "admin"`. El rol se asigna a mano (Tinker, *seeder* o un panel de administración).

## 3. Policies: las reglas en un solo sitio

Una **Policy** reúne las reglas de autorización de un modelo. Responde a la pregunta: «¿este usuario puede hacer esta acción con este objeto?».

```bash
php artisan make:policy NotePolicy --model=Note
```

En `app/Policies/NotePolicy.php`:

```php
<?php

namespace App\Policies;

use App\Models\Note;
use App\Models\User;

class NotePolicy
{
    // Se ejecuta antes que el resto: el administrador puede con todo
    public function before(User $user, string $ability): ?bool
    {
        return $user->isAdmin() ? true : null;
    }

    public function viewAny(User $user): bool
    {
        return true;
    }

    public function view(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }

    public function create(User $user): bool
    {
        return true;
    }

    public function update(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }

    public function delete(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }
}
```

* `before` devuelve `true` para los administradores (se salta el resto) y `null` para los demás (se aplica la regla del método).
* Laravel encuentra la policy automáticamente porque se llama `NotePolicy` y está en `app/Policies`.

## 4. Aplicar la autorización en el controlador

Con **`Gate::authorize`** se comprueba la policy. Si la regla devuelve `false`, Laravel lanza una excepción que se convierte en un **`403`** en JSON, y el resto del método no se ejecuta.

```php
<?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Http\Requests\NoteRequest;
use App\Http\Resources\NoteResource;
use App\Models\Note;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\AnonymousResourceCollection;
use Illuminate\Http\Response;
use Illuminate\Support\Facades\Gate;

class NoteController extends Controller
{
    public function index(Request $request): AnonymousResourceCollection
    {
        $user = $request->user();

        // El administrador ve todas las notas; el resto, solo las suyas
        $query = $user->isAdmin() ? Note::query() : $user->notes();

        return NoteResource::collection($query->latest()->paginate(10));
    }

    public function store(NoteRequest $request): JsonResponse
    {
        // La nota se crea a nombre del usuario autenticado
        $note = $request->user()->notes()->create($request->validated());

        return (new NoteResource($note))->response()->setStatusCode(201);
    }

    public function show(Note $note): NoteResource
    {
        Gate::authorize('view', $note);

        return new NoteResource($note);
    }

    public function update(NoteRequest $request, Note $note): NoteResource
    {
        Gate::authorize('update', $note);

        $note->update($request->validated());

        return new NoteResource($note);
    }

    public function destroy(Note $note): Response
    {
        Gate::authorize('delete', $note);

        $note->delete();

        return response()->noContent();
    }
}
```

!!!tenencuenta "`user_id` nunca llega del cliente"
    En `store`, el propietario sale de `$request->user()`, no de los datos enviados. `NoteRequest` no tiene regla para `user_id`, así que `validated()` lo descartaría aunque el cliente lo enviara.

!!!tenencuenta "¿Y `authorizeResource()`?"
    En tutoriales antiguos verás `$this->authorizeResource(Note::class)` en el constructor. Desde Laravel 11, el `Controller` base está vacío y ese método no existe si no se añade a mano el trait `AuthorizesRequests`. `Gate::authorize` es la forma actual y deja claro qué se comprueba en cada método.

## 5. Decirle a Vue qué puede hacer

Vue necesita saber si debe mostrar los botones **Editar** y **Borrar**. En lugar de copiar las reglas de la policy en JavaScript (y mantenerlas en dos sitios), la API lo indica en cada nota. En `NoteResource`:

```php hl_lines="9-12"
public function toArray(Request $request): array
{
    return [
        'id' => $this->id,
        'titulo' => $this->title,
        'descripcion' => $this->description,
        'fecha' => $this->date_at->format('Y-m-d'),
        'estado' => $this->done ? 'Completada' : 'Pendiente',
        'permisos' => [
            'editar' => $request->user()?->can('update', $this->resource) ?? false,
            'borrar' => $request->user()?->can('delete', $this->resource) ?? false,
        ],
    ];
}
```

En `NotesPanel.vue`:

```vue
<button v-if="note.permisos.borrar" @click="remove(note.id)">Borrar</button>
```

Las reglas siguen en un solo sitio (la policy). Si cambian, Vue se adapta solo.

Y si, aun así, llega un `403` (por ejemplo, porque otro usuario ha cambiado algo), el `handle()` del apartado 11.2 lo trata:

```js
else if (status === 403) alert("No tienes permiso para esta acción.");
```

## 6. Comprobarlo

1. Crea dos usuarios normales (A y B) y un administrador:
    ```php
    $admin = App\Models\User::create(['name' => 'Admin', 'email' => 'admin@testear.com', 'password' => 'password']);
    $admin->role = 'admin';
    $admin->save();
    ```
2. Con A, crea dos notas. Con B, crea una.
3. Con A solo ves tus dos notas; con B, solo la suya; con el administrador, las tres.
4. Desde REST Client, con el token de B, intenta borrar una nota de A: `DELETE /api/notes/{id}` debe responder **`403`**.

Y con tests automáticos:

```php
public function test_no_puede_borrar_notas_ajenas(): void
{
    $note = Note::factory()->for(User::factory())->create();

    Sanctum::actingAs(User::factory()->create());

    $this->deleteJson("/api/notes/{$note->id}")->assertForbidden();
}

public function test_el_administrador_puede_borrar_cualquier_nota(): void
{
    $note = Note::factory()->for(User::factory())->create();

    Sanctum::actingAs(User::factory()->create(['role' => 'admin']));

    $this->deleteJson("/api/notes/{$note->id}")->assertNoContent();
}
```

!!!tenencuenta "`role` en las factories"
    `User::factory()->create(['role' => 'admin'])` funciona aunque `role` no esté en `$fillable`: las factories no pasan por la protección de asignación masiva.

## 7. Resumen

| Concepto | Dónde |
| --- | --- |
| Propietario de un recurso | Clave foránea `user_id` y relaciones |
| Roles | Campo `role` y método `isAdmin()` |
| Reglas | `NotePolicy` |
| Aplicar las reglas | `Gate::authorize()` en el controlador → `403` |
| Filtrar listados | Consulta según el usuario en `index` |
| Adaptar la interfaz | Campo `permisos` en el Resource y `v-if` en Vue |
