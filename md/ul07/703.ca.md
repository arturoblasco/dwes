# <img src="../../img/laravel_azul.svg" width="40"> 11.3. Autorització

Ja sabem **qui** és l'usuari (autenticació). Ara decidim **què pot fer** (autorització): cada usuari només veu i modifica les seues notes, i un administrador pot fer-ho amb totes.

| | Pregunta | Si falla |
| --- | --- | --- |
| **Autenticació** | Qui eres? | `401 Unauthorized` |
| **Autorització** | Pots fer això amb este recurs? | `403 Forbidden` |

> La seguretat real està sempre al **backend**. Vue només adapta la interfície perquè l'usuari no veja botons que no pot utilitzar.

## 1. Propietari de cada nota

Cada nota pertany a un usuari. Afegim la clau forana:

```bash
php artisan make:migration add_user_id_to_notes_table
```

```php
public function up(): void
{
    Schema::table('notes', function (Blueprint $table) {
        $table->foreignId('user_id')->nullable()->after('id')
              ->constrained()->cascadeOnDelete();
    });
}

public function down(): void
{
    Schema::table('notes', function (Blueprint $table) {
        $table->dropConstrainedForeignId('user_id');
    });
}
```

És `nullable` per a no trencar les notes que ja existixen. Els pots assignar un propietari amb Tinker: `App\Models\Note::whereNull('user_id')->update(['user_id' => 1])`.

Relacions als models (unitat 8):

```php
// app/Models/User.php
public function notes(): HasMany
{
    return $this->hasMany(Note::class);
}

// app/Models/Note.php
public function user(): BelongsTo
{
    return $this->belongsTo(User::class);
}
```

## 2. Rols

Per a distingir els administradors, afegim un camp `role` a `users`:

```bash
php artisan make:migration add_role_to_users_table
```

```php
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->string('role')->default('user')->after('email');
    });
}

public function down(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->dropColumn('role');
    });
}
```

```bash
php artisan migrate
```

Al model `User`, un mètode que fa el codi més llegible:

```php
public function isAdmin(): bool
{
    return $this->role === 'admin';
}
```

!!!tenencuenta "No afiges `role` a `$fillable`"
    Si `role` estiguera a `$fillable`, algú podria registrar-se enviant `"role": "admin"`. El rol s'assigna a mà (Tinker, *seeder* o un tauler d'administració).

## 3. Policies: les regles en un sol lloc

Una **Policy** reunix les regles d'autorització d'un model. Respon a la pregunta: «este usuari pot fer esta acció amb este objecte?».

```bash
php artisan make:policy NotePolicy --model=Note
```

A `app/Policies/NotePolicy.php`:

```php
<?php

namespace App\Policies;

use App\Models\Note;
use App\Models\User;

class NotePolicy
{
    // Se ejecuta antes que el resto: el administrador puede con todo
    public function before(User $user, string $ability): ?bool
    {
        return $user->isAdmin() ? true : null;
    }

    public function viewAny(User $user): bool
    {
        return true;
    }

    public function view(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }

    public function create(User $user): bool
    {
        return true;
    }

    public function update(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }

    public function delete(User $user, Note $note): bool
    {
        return $user->id === $note->user_id;
    }
}
```

* `before` torna `true` per als administradors (se salta la resta) i `null` per als altres (s'aplica la regla del mètode).
* Laravel troba la policy automàticament perquè es diu `NotePolicy` i està a `app/Policies`.

## 4. Aplicar l'autorització al controlador

Amb **`Gate::authorize`** es comprova la policy. Si la regla torna `false`, Laravel llança una excepció que es convertix en un **`403`** en JSON, i la resta del mètode no s'executa.

```php
<?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Http\Requests\NoteRequest;
use App\Http\Resources\NoteResource;
use App\Models\Note;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\AnonymousResourceCollection;
use Illuminate\Http\Response;
use Illuminate\Support\Facades\Gate;

class NoteController extends Controller
{
    public function index(Request $request): AnonymousResourceCollection
    {
        $user = $request->user();

        // El administrador ve todas las notas; el resto, solo las suyas
        $query = $user->isAdmin() ? Note::query() : $user->notes();

        return NoteResource::collection($query->latest()->paginate(10));
    }

    public function store(NoteRequest $request): JsonResponse
    {
        // La nota se crea a nombre del usuario autenticado
        $note = $request->user()->notes()->create($request->validated());

        return (new NoteResource($note))->response()->setStatusCode(201);
    }

    public function show(Note $note): NoteResource
    {
        Gate::authorize('view', $note);

        return new NoteResource($note);
    }

    public function update(NoteRequest $request, Note $note): NoteResource
    {
        Gate::authorize('update', $note);

        $note->update($request->validated());

        return new NoteResource($note);
    }

    public function destroy(Note $note): Response
    {
        Gate::authorize('delete', $note);

        $note->delete();

        return response()->noContent();
    }
}
```

!!!tenencuenta "`user_id` mai no arriba del client"
    A `store`, el propietari ix de `$request->user()`, no de les dades enviades. `NoteRequest` no té regla per a `user_id`, així que `validated()` el descartaria encara que el client l'enviara.

!!!tenencuenta "I `authorizeResource()`?"
    En tutorials antics veuràs `$this->authorizeResource(Note::class)` al constructor. Des de Laravel 11, el `Controller` base està buit i eixe mètode no existix si no s'afig a mà el trait `AuthorizesRequests`. `Gate::authorize` és la manera actual i deixa clar què es comprova en cada mètode.

## 5. Dir-li a Vue què pot fer

Vue necessita saber si ha de mostrar els botons **Editar** i **Borrar**. En lloc de copiar les regles de la policy en JavaScript (i mantindre-les en dos llocs), l'API ho indica en cada nota. A `NoteResource`:

```php hl_lines="9-12"
public function toArray(Request $request): array
{
    return [
        'id' => $this->id,
        'titulo' => $this->title,
        'descripcion' => $this->description,
        'fecha' => $this->date_at->format('Y-m-d'),
        'estado' => $this->done ? 'Completada' : 'Pendiente',
        'permisos' => [
            'editar' => $request->user()?->can('update', $this->resource) ?? false,
            'borrar' => $request->user()?->can('delete', $this->resource) ?? false,
        ],
    ];
}
```

A `NotesPanel.vue`:

```vue
<button v-if="note.permisos.borrar" @click="remove(note.id)">Borrar</button>
```

Les regles continuen en un sol lloc (la policy). Si canvien, Vue s'adapta tot sol.

I si, tot i això, arriba un `403` (per exemple, perquè un altre usuari ha canviat alguna cosa), el `handle()` de l'apartat 11.2 el tracta:

```js
else if (status === 403) alert("No tienes permiso para esta acción.");
```

## 6. Comprovar-ho

1. Crea dos usuaris normals (A i B) i un administrador:
    ```php
    $admin = App\Models\User::create(['name' => 'Admin', 'email' => 'admin@testear.com', 'password' => 'password']);
    $admin->role = 'admin';
    $admin->save();
    ```
2. Amb A, crea dues notes. Amb B, crea'n una.
3. Amb A només veus les teues dues notes; amb B, només la seua; amb l'administrador, les tres.
4. Des de REST Client, amb el token de B, intenta esborrar una nota d'A: `DELETE /api/notes/{id}` ha de respondre **`403`**.

I amb tests automàtics:

```php
public function test_no_puede_borrar_notas_ajenas(): void
{
    $note = Note::factory()->for(User::factory())->create();

    Sanctum::actingAs(User::factory()->create());

    $this->deleteJson("/api/notes/{$note->id}")->assertForbidden();
}

public function test_el_administrador_puede_borrar_cualquier_nota(): void
{
    $note = Note::factory()->for(User::factory())->create();

    Sanctum::actingAs(User::factory()->create(['role' => 'admin']));

    $this->deleteJson("/api/notes/{$note->id}")->assertNoContent();
}
```

!!!tenencuenta "`role` a les factories"
    `User::factory()->create(['role' => 'admin'])` funciona encara que `role` no estiga a `$fillable`: les factories no passen per la protecció d'assignació massiva.

## 7. Resum

| Concepte | On |
| --- | --- |
| Propietari d'un recurs | Clau forana `user_id` i relacions |
| Rols | Camp `role` i mètode `isAdmin()` |
| Regles | `NotePolicy` |
| Aplicar les regles | `Gate::authorize()` al controlador → `403` |
| Filtrar llistats | Consulta segons l'usuari a `index` |
| Adaptar la interfície | Camp `permisos` al Resource i `v-if` en Vue |
