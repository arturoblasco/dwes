# <img src="../../img/laravel_azul.svg" width="40"> 10.0. Introducción

Hasta ahora, nuestras aplicaciones Laravel devolvían **páginas HTML** generadas con Blade. En esta unidad el backend cambia de papel: deja de pintar pantallas y pasa a ofrecer un **servicio web** que devuelve **datos en JSON**. Cualquier cliente (una SPA en Vue, una app móvil, otro servidor) puede consumir esos datos.

> *"Usamos un backend con API para que la aplicación no dependa de cómo se ve,
> sino de cómo funciona, y poder usar los datos desde cualquier sitio."*

## 1. ¿Qué es una API REST que devuelve JSON?

Es un backend que:

- recibe peticiones HTTP (`GET`, `POST`, `PUT`/`PATCH`, `DELETE`) sobre **recursos** identificados por URL (`/api/notes`, `/api/notes/5`);
- procesa los datos (base de datos, reglas de negocio, permisos);
- responde con **JSON** y con un **código de estado HTTP** que indica qué ha pasado.

```json
{
    "data": {
        "id": 5,
        "titulo": "Comprar pan",
        "estado": "Pendiente"
    }
}
```

## 2. ¿Para qué sirve?

| Ventaja | En la práctica |
| --- | --- |
| **Separar frontend y backend** | El backend gestiona datos, reglas y seguridad. El frontend solo muestra. Se puede cambiar uno sin tocar el otro. |
| **Reutilizar el backend** | La misma API sirve a una web en Vue, a una app móvil o a otro sistema. |
| **Comunicación estándar** | HTTP + JSON: cualquier lenguaje sabe leerlo. |
| **Trabajo en equipo** | Quien hace la API y quien hace el frontend avanzan en paralelo si acuerdan el *contrato* (rutas, JSON y errores). |
| **Seguridad** | El cliente nunca accede a la base de datos: solo a lo que la API decide exponer. |

| Sin API (todo junto) | Con API JSON |
| --- | --- |
| HTML y PHP mezclados | Frontend y backend separados |
| Poco reutilizable | Muy reutilizable |
| Difícil de escalar | Escalable |
| Acoplado | Modular |

## 3. REST en cuatro reglas

1. **Recursos con nombre**: las URL nombran cosas, no acciones (`/api/notes`, no `/api/getNotes`).
2. **El método HTTP indica la acción**: `GET` lee, `POST` crea, `PUT`/`PATCH` modifica y `DELETE` elimina.
3. **Sin estado (*stateless*)**: cada petición lleva todo lo necesario (por ejemplo, el token). El servidor no recuerda la petición anterior.
4. **Códigos de estado con significado**: `200`, `201`, `204`, `401`, `403`, `404`, `422`… (se detallan en el apartado 10.2).
