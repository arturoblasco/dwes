## 1. Controlador API y rutas

### 1.1. Generar el controlador

El *flag* **`--api`** genera un controlador con los cinco métodos de una API (sin `create` ni `edit`, que solo sirven para mostrar formularios HTML):

```bash
php artisan make:controller Api/NoteController --api --model=Note
```

Se crea `app/Http/Controllers/Api/NoteController.php` con `index`, `store`, `show`, `update` y `destroy`. Al indicar `--model=Note`, los métodos ya reciben `Note $note` (*route model binding*).

### 1.2. Rutas

En `routes/api.php`:

```php
use App\Http\Controllers\Api\NoteController;

Route::apiResource('notes', NoteController::class);
```

`apiResource` crea las cinco rutas REST. Si solo quieres algunas, usa `only` o `except`, por ejemplo una API de solo lectura:

```php
Route::apiResource('notes', NoteController::class)->only(['index', 'show']);
```

Comprueba las rutas:

```bash
php artisan route:list --path=api/notes
```

## 2. Códigos de estado HTTP

Una API comunica el resultado con el **código de estado**, no solo con el cuerpo:

| Código | Nombre | Cuándo se usa |
| --- | --- | --- |
| `200 OK` | Éxito | Lectura o modificación correcta que devuelve datos |
| `201 Created` | Creado | Se ha creado un recurso (`POST`) |
| `204 No Content` | Sin contenido | Éxito sin cuerpo de respuesta (típico de `DELETE`) |
| `401 Unauthorized` | No autenticado | Falta el token o la sesión, o no son válidos |
| `403 Forbidden` | Prohibido | Autenticado, pero sin permiso para esa acción |
| `404 Not Found` | No encontrado | El recurso no existe |
| `422 Unprocessable Content` | Datos no válidos | Ha fallado la validación |
| `500 Internal Server Error` | Error del servidor | Error inesperado |

## 3. API Resources: controlar el JSON de salida

Devolver directamente el modelo (`return $note;`) expone **todas** sus columnas con sus nombres internos. Un **API Resource** decide qué campos salen y con qué formato. Así el JSON (el *contrato* con el cliente) no cambia aunque cambie la base de datos.

```bash
php artisan make:resource NoteResource
```

En `app/Http/Resources/NoteResource.php`:

```php
public function toArray(Request $request): array
{
    return [
        'id' => $this->id,
        'titulo' => $this->title,
        'descripcion' => $this->description,
        'fecha' => $this->date_at->format('Y-m-d'),
        'estado' => $this->done ? 'Completada' : 'Pendiente',
        'creada' => $this->created_at->toIso8601String(),
    ];
}
```

!!!tenencuenta "`date_at` debe ser una fecha"
    `$this->date_at->format(...)` solo funciona si el modelo convierte `date_at` en fecha con `casts()` (`'date_at' => 'date'`), como en el modelo del principio del apartado.

Un Resource **ya envuelve** la respuesta en una clave `data`, así que no hace falta construir el JSON a mano con `response()->json([...])`:

| En el controlador | Respuesta |
| --- | --- |
| `return new NoteResource($note);` | `{ "data": { "id": 5, ... } }` con `200` |
| `return NoteResource::collection(Note::all());` | `{ "data": [ ... ] }` con `200` |
| `return NoteResource::collection(Note::paginate(10));` | `{ "data": [...], "links": {...}, "meta": {...} }` con `200` |

!!!teolaravel "Paginación gratis"
    Si pasas un paginador a `collection()`, la respuesta incluye `links` (primera, anterior, siguiente y última página) y `meta` (página actual, total, elementos por página…). El cliente pide otras páginas con `?page=2`.
    ```json
    {
        "data": [ { "id": 1, "titulo": "..." } ],
        "links": { "first": ".../api/notes?page=1", "next": ".../api/notes?page=2", ... },
        "meta": { "current_page": 1, "per_page": 10, "total": 23, ... }
    }
    ```

Si necesitas añadir información junto a `data` (por ejemplo, un mensaje), usa `additional`:

```php
return (new NoteResource($note))->additional(['message' => 'Nota creada correctamente.']);
```

## 4. Validación con Form Requests

Igual que con los formularios web, los datos que llegan a la API se validan **antes** de guardarlos.

```bash
php artisan make:request NoteRequest
```

!!!tip "Si ya tienes un `NoteRequest`"
    Si en una práctica anterior creaste un `NoteRequest` para formularios Blade, puedes reutilizarlo: las reglas son las mismas. Laravel ya sabe responder en JSON cuando la petición viene de la API.

En `app/Http/Requests/NoteRequest.php`:

```php
public function authorize(): bool
{
    return true;
}

public function rules(): array
{
    return [
        'title' => ['required', 'string', 'max:255'],
        'description' => ['required', 'string'],
        'date_at' => ['required', 'date'],
        'done' => ['sometimes', 'boolean'],
    ];
}
```

Si la validación falla, Laravel responde automáticamente con **`422`** y los errores por campo (gracias a la configuración del apartado 10.1, aunque el cliente no envíe `Accept: application/json`):

```json
{
    "message": "The title field is required. (and 1 more error)",
    "errors": {
        "title": ["The title field is required."],
        "date_at": ["The date at field is required."]
    }
}
```

!!!tenencuenta "Mensajes en castellano"
    Para que los mensajes de validación salgan en castellano, sigue el apartado *5.7. Traducir los mensajes de error* de [9.2. Sistema de validación](../ul04/402.md). Funciona igual para formularios y para la API.

!!!tenencuenta "Acentos escapados (`ó`)"
    En la respuesta verás los acentos como `ó`. Es JSON válido: cualquier cliente (navegador, Vue, Postman) lo decodifica y muestra «ó». No hace falta cambiar nada.

### 4.1. `validated()` en lugar de `all()`

En el controlador usaremos **`$request->validated()`**, que devuelve **solo** los campos que tienen regla de validación. Si un cliente envía campos de más (por ejemplo `"role": "admin"`), se descartan:

```php
$request->all();
// ['title' => '...', 'description' => '...', 'date_at' => '...', 'role' => 'admin']

$request->validated();
// ['title' => '...', 'description' => '...', 'date_at' => '...']
```

`$fillable` en el modelo ya protege de la asignación masiva, pero `validated()` añade una segunda barrera y deja claro qué datos se aceptan.

## 5. El controlador completo

```php
<?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Http\Requests\NoteRequest;
use App\Http\Resources\NoteResource;
use App\Models\Note;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Resources\Json\AnonymousResourceCollection;
use Illuminate\Http\Response;

class NoteController extends Controller
{
    public function index(): AnonymousResourceCollection
    {
        return NoteResource::collection(Note::latest()->paginate(10));
    }

    public function store(NoteRequest $request): JsonResponse
    {
        $note = Note::create($request->validated());

        return (new NoteResource($note))
            ->response()
            ->setStatusCode(201);
    }

    public function show(Note $note): NoteResource
    {
        return new NoteResource($note);
    }

    public function update(NoteRequest $request, Note $note): NoteResource
    {
        $note->update($request->validated());

        return new NoteResource($note);
    }

    public function destroy(Note $note): Response
    {
        $note->delete();

        return response()->noContent();
    }
}
```

Fíjate en que:

* `show`, `update` y `destroy` reciben `Note $note`. Si el ID no existe, Laravel responde **`404`** antes de entrar en el método: no hace falta `findOrFail` ni `try`/`catch`.
* `store` responde **`201`** y `destroy` responde **`204`** sin cuerpo.
* Ningún método construye el JSON a mano: el formato lo decide `NoteResource`.

| Método | Respuesta correcta | Respuestas de error posibles |
| --- | --- | --- |
| `index` | `200` + lista paginada | — |
| `store` | `201` + nota creada | `422` |
| `show` | `200` + nota | `404` |
| `update` | `200` + nota modificada | `404`, `422` |
| `destroy` | `204` | `404` |
