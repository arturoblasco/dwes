# <img src="../../img/laravel_azul.svg" width="40"> Práctica guiada: API REST de productos

### Objetivo

Aplicar todo lo visto en la unidad para construir una **API REST de productos** completa: rutas, controlador, formato de salida, validación, errores en JSON, autenticación con tokens, pruebas y documentación.

Puedes partir del proyecto de las prácticas anteriores (que ya tiene productos) o de uno nuevo. En los ejemplos, el proyecto está en `http://testear.test`.

---

### FASE 1: Preparar el proyecto

1. Arranca los servicios (Docker con `sail up -d`, o Nginx y MySQL en Laragon).
2. Si todavía no tienes rutas API, ejecuta `php artisan install:api` y responde que sí a las migraciones.
3. En `bootstrap/app.php`, configura que los errores de las rutas `api/*` se devuelvan siempre en JSON (apartado [10.1](501.md)).

### FASE 2: Tabla y modelo (si no los tienes)

| Campo | Tipo | Restricciones |
| --- | --- | --- |
| `id` | `id()` | Clave primaria |
| `name` | `string` | Obligatorio |
| `description` | `text` | Puede ser nulo |
| `price` | `decimal(8,2)` | Obligatorio |
| `stock` | `integer` | Obligatorio, por defecto 0 |
| `created_at`, `updated_at` | `timestamps()` | Automáticos |

```bash
php artisan make:model Product -mf
```

Define `$fillable` en el modelo y un `ProductFactory` con datos realistas. Rellena la tabla con unos 25 productos (con un *seeder* o con Tinker: `Product::factory(25)->create()`).

### FASE 3: Controlador y rutas

1. Crea el controlador con `php artisan make:controller Api/ProductController --api --model=Product`.
2. Registra las rutas con `Route::apiResource('products', ...)`.
3. Comprueba que existen las cinco rutas con `php artisan route:list --path=api/products`.

### FASE 4: Formato de salida con `ProductResource`

Crea `ProductResource` con esta estructura:

```json
{
    "id": 1,
    "nombre": "Camiseta",
    "descripcion": "Camiseta de algodón",
    "precio": 19.99,
    "precio_formateado": "19,99 €",
    "stock": 25,
    "disponible": true
}
```

* `precio` es un número (`(float) $this->price`), no un texto.
* `disponible` es `true` si `stock > 0`.

Implementa los cinco métodos **sin construir el JSON a mano**:

| Método | Respuesta |
| --- | --- |
| `index` | Productos paginados de 10 en 10 (`data`, `links` y `meta`) |
| `store` | `201` + producto creado |
| `show` | `200` + producto |
| `update` | `200` + producto modificado |
| `destroy` | `204` sin cuerpo |

**Extra**: permite filtrar con `GET /api/products?search=camiseta` (busca en `name`) y `?available=1` (solo con `stock > 0`). Pista: `Product::query()->when($request->search, fn ($q, $s) => $q->where('name', 'like', "%{$s}%"))`.

### FASE 5: Validación con `ProductRequest`

| Campo | Reglas |
| --- | --- |
| `name` | obligatorio, texto, entre 3 y 255 caracteres |
| `description` | opcional, texto, mínimo 10 caracteres |
| `price` | obligatorio, numérico, entre 0 y 9999.99 |
| `stock` | obligatorio, entero, entre 0 y 10000 |

Usa `$request->validated()` en `store` y `update`. Los mensajes de error deben salir en castellano.

### FASE 6: Autenticación con tokens

1. Añade `HasApiTokens` al modelo `User`.
2. Crea `TokenAuthController` con `login` y `logout` (apartado [10.4](504.md)).
3. Deja **públicas** las rutas de lectura (`index` y `show`) y protege con `auth:sanctum` las de escritura (`store`, `update` y `destroy`). Pista: dos llamadas a `apiResource`, una con `only` y otra con `except`.
4. Crea un usuario de prueba.

### FASE 7: Pruebas manuales

Crea `products.rest` con estas peticiones, todas con `Accept: application/json`:

1. Login y guardado del token (`# @name login`).
2. Listar productos, segunda página y búsqueda.
3. Ver un producto.
4. Crear un producto **sin token** → `401`.
5. Crear un producto con token → `201`.
6. Crear un producto con precio negativo y stock de texto → `422`.
7. Modificar un producto → `200`.
8. Ver un producto que no existe → `404`.
9. Eliminar un producto → `204`.
10. Logout.

### FASE 8: Pruebas automáticas

Crea `tests/Feature/ProductApiTest.php` con, al menos, estos tests:

* el listado responde `200` y tiene `data`, `links` y `meta`;
* crear sin autenticación responde `401`;
* crear con `Sanctum::actingAs` responde `201` y el producto está en la base de datos;
* datos no válidos responden `422` con errores en `price` y `stock`;
* un producto inexistente responde `404`;
* eliminar responde `204` y el producto ya no está en la base de datos.

Todos deben pasar con `php artisan test`.

### FASE 9: Documentación

1. Instala Scribe y documenta el grupo *Productos*: descripción de cada método, parámetros de búsqueda y ejemplos de respuesta `201` y `422`.
2. Marca con `@authenticated` los métodos que exigen token.
3. Genera la documentación con `php artisan scribe:generate`.

    Entrega un **PDF** con un título para cada captura y el enlace al repositorio del proyecto.

    **Capturas requeridas**

    1. `php artisan route:list --path=api` con las rutas de productos y de autenticación.
    2. El código de `ProductResource`, `ProductRequest` y `ProductController`.
    3. En REST Client, las respuestas de las peticiones 1, 2, 4, 5, 6, 8 y 9 de la fase 7, con el **código de estado visible**.
    4. La salida de `php artisan test` con todos los tests superados.
    5. La página de documentación generada por Scribe, con el método *Crear producto* desplegado.

    **Se comprobará que**

    * cada ruta responde con el código de estado correcto;
    * ninguna respuesta se construye a mano: el formato lo decide `ProductResource`;
    * los errores (`401`, `404`, `422`) llegan siempre en JSON;
    * las rutas de escritura exigen token y las de lectura no;
    * todos los tests pasan;
    * la documentación describe todas las rutas.
